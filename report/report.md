# 과제 보고서: 농업 로봇의 엣지 AI와 클라우드 AI 선택

## 1. 선택한 사례
논밭에서 카메라로 작물과 잡초를 구분하여 잡초만 제거하는 제초 로봇

## 2. 판단 결과
**엣지 AI가 적합하다.**

## 3. 기준별 분석

### 속도
- 로봇이 움직이는 중에 영상을 보고 즉시 잡초 위치를 판단해야 한다.
- 엣지 AI는 인터넷을 거치지 않아 응답 지연이 짧다.
- 클라우드 AI는 영상 전송과 결과 수신에 시간이 걸려 판단이 늦어진다.
- 따라서 속도 면에서는 엣지 AI가 유리하다.

### 비용
- 엣지 AI는 로봇에 들어가는 연산 장치 구입비가 초기에 한 번 발생한다.
- 클라우드 AI는 영상을 보낼 때마다 통신비와 서버 사용료가 발생한다.
- 제초 로봇은 넓은 논밭에서 오래 작동하므로 영상 처리량이 많다.
- 사용량이 많을수록 클라우드 비용이 누적되므로, 장기적으로는 엣지 AI가 유리하다.

### 오프라인
- 논밭은 통신 환경이 불안정하거나 인터넷이 아예 되지 않는 곳이 많다.
- 엣지 AI는 인터넷 없이 로봇 안에서 동작한다.
- 클라우드 AI는 연결이 끊기면 로봇이 멈춘다.
- 따라서 오프라인 동작 면에서는 엣지 AI가 유리하다.

### 프라이버시
- 농장 영상에는 개인 정보가 거의 없어 이 기준의 중요도는 높지 않다.
- 그래도 엣지 AI는 영상이 로봇 안에 머물러 외부 유출 위험이 없다.
- 클라우드 AI는 영상을 외부로 전송하는 과정에서 유출 위험이 생긴다.
- 따라서 프라이버시 면에서도 엣지 AI가 유리하지만, 결정적인 근거는 아니다.

### 모델 크기
- 작물과 잡초를 구분하는 일은 비교적 단순한 영상 인식이다.
- 이 정도 작업은 작은 모델로 충분하여 엣지 장치에서도 돌릴 수 있다.
- 큰 모델이 필요한 작업이 아니므로 클라우드를 쓸 이유가 없다.
- 따라서 모델 크기 면에서도 엣지 AI로 충분하다.

## 4. 종합 정리

| 기준 | 유리한 쪽 | 이유 |
|---|---|---|
| 속도 | 엣지 AI | 이동 중 즉시 판단 필요 |
| 비용 | 엣지 AI | 사용량이 많아 클라우드 비용 누적 |
| 오프라인 | 엣지 AI | 논밭은 인터넷이 불안정 |
| 프라이버시 | 엣지 AI | 중요도는 낮으나 유출 위험 없음 |
| 모델 크기 | 엣지 AI | 작은 모델로 충분 |

## 5. 결론
다섯 가지 기준 모두 엣지 AI가 유리하다. 특히 인터넷이 불안정한 논밭에서 즉시 판단해야 한다는 점이 가장 결정적인 근거이다. 따라서 농업 제초 로봇에는 엣지 AI를 적용하는 것이 적합하다.


# PRD: 인원 연동 팬 제어 시스템 (가칭 OccuFan)

## 제품 개요

| 항목 | 내용 |
|---|---|
| 제품명 | 인원 연동 팬 제어 시스템 (가칭 OccuFan) |
| 주요 입력 데이터 | 실내 천장·벽면 카메라 영상 (프레임 단위), 방 영역 설정값(좌표) |
| 주요 출력(행동) | 실내 인원 수 → 팬 풍량 단계(30 / 50 / 75 / 100 %) 결정 → 송풍기 인버터에 속도 지령(0–10 V) 전송 |
| 대상 공간 | 인원 변동이 큰 실내 공간 (대학 강의실·회의실 등), 송풍기에 인버터(VFD)가 설치된 곳 (가정) |

## 1. 문제 정의 (Problem Statement)

### 현재 존재하는 문제
- 많은 건물에서 송풍기(AHU·환기팬)는 사람이 있든 없든 **고정 풍량(상시 100 %)** 으로 운전한다.
- 인원이 적을 때는 과잉 환기로 전력과 외기 냉난방 부하가 낭비되고, 인원이 몰릴 때는 환기가 부족해 실내 공기질이 나빠진다.

### 기존 방식의 한계
- **시간표 기반 운전**: 실제 사용 여부와 무관하게 정해진 시각에 운전한다. 휴강·공실을 반영하지 못한다.
- **CO₂ 센서 기반 제어**: 인원이 바뀐 뒤 농도가 변할 때까지 수 분 이상 늦게 반응한다.
- **인체 감지 센서(PIR)**: "있다/없다"만 알 수 있어 인원 규모에 따른 단계 제어가 불가능하다.

### 핵심 가치
- 인원 수를 **즉시** 파악해 필요한 만큼만 환기한다 → 송풍기 전력과 외기 부하 절감.
- 영상 원본을 저장·외부 전송하지 않고 기기 안에서 처리한다 → 개인정보 부담 최소화.

### 왜 AI가 필요한가
- 사람의 수를 세려면 영상 속 사람을 구분하고 같은 사람을 중복 없이 이어서 봐야 한다. 규칙 기반 영상처리(배경 차분 등)는 조명 변화와 사람이 겹치는 상황에서 오차가 크다.
- 사람 검출 AI 모델(YOLO 계열)과 추적·카운트 후처리(supervision)를 조합하면 현장 조건에서 안정적으로 인원을 셀 수 있다.

## 2. 사용자 시나리오 (User Scenario)

| 단계 | 내용 |
|---|---|
| 1. 설치 | 관리자가 카메라와 엣지 기기(Raspberry Pi 5)를 실내에 설치하고, ESP32-S3 제어 모듈을 송풍기 인버터의 0–10 V 입력에 연결한다. 대시보드에서 방 영역(다각형)과 단계 기준 인원을 설정한다. |
| 2. 데이터 수집 | 카메라가 영상을 연속 촬영하고, 엣지 기기가 프레임을 메모리에서만 처리한 뒤 즉시 폐기한다. |
| 3. 분석 | AI 모델이 사람을 검출하고, 중복 박스 제거와 추적을 거쳐 설정한 방 영역 안의 인원 수를 계산한다. |
| 4. 판단 | 최근 2초 인원값을 평활화(중앙값)하고, 인원 기준표와 히스테리시스·최소 유지시간 규칙을 적용해 팬 단계를 결정한다. |
| 5. 제어 | 결정된 단계를 MQTT로 ESP32-S3에 보내고, ESP32-S3가 인버터에 해당 풍량의 속도 지령을 출력한다. |
| 6. 확인·후속 | 관리자는 대시보드에서 현재 인원, 팬 단계, 일별 전력 절감 추정치를 확인한다. 카메라 오류·인원 급변 등 이상 시 알림을 받고 설정을 조정한다. |

### 단계 기준표 (가정)

| 평활 인원 | 팬 단계 | 풍량 지령 |
|---|---|---|
| 0–4명 | 0단계 | 30 % (최소 환기 유지) |
| 5–14명 | 1단계 | 50 % |
| 15–24명 | 2단계 | 75 % |
| 25명 이상 | 3단계 | 100 % |

- 내릴 때는 기준보다 2명 더 줄어야 단계를 내린다 (히스테리시스).
- 한 단계는 최소 60초 이상 유지한다 (잦은 전환 방지).
- 근거(가정): 1인당 발열량은 현열 약 75 W, 잠열 약 55 W로 보고, 인원이 늘수록 환기·냉방 필요량이 커지는 방향으로 단계를 정했다.

## 4. 기술 스택 (Technology Stack)

| 구성 | 사용 기술 | 선정 이유 |
|---|---|---|
| 카메라 | Raspberry Pi Camera Module 3 (CSI) 또는 USB 카메라 | Pi 5와 직접 연결되고 저렴하며 자료가 많다. |
| 센서 | CO₂ 센서 (NDIR, 검증용) | 제어에는 쓰지 않고 "환기 품질이 유지되는가"를 검증하는 기준값으로만 쓴다. |
| MCU | ESP32-S3 | 저가·저전력이며 Wi-Fi 내장. PWM/DAC 모듈로 0–10 V 지령을 만들기 쉽다. |
| Edge AI | Raspberry Pi 5 (CPU, ONNX Runtime) | 별도 가속기 없이 경량 모델이 현장에서 돈다. 클라우드 왕복 지연이 없다. |
| AI 모델 | YOLO nano 계열 (COCO person 클래스) | 경량이라 CPU에서 실시간 처리가 가능하다. 천장 시점 정확도가 낮으면 머리·어깨 데이터로 파인튜닝한다. |
| 후처리 | supervision (NMS, ByteTrack, PolygonZone) | 중복 박스 제거, 같은 사람 추적, 방 영역 내 카운트를 한 번에 처리한다. |
| 서버 | FastAPI (Pi 5 내 동작) | 가볍고 API 설계가 쉬워 대시보드·제어 로직과 연결하기 좋다. |
| 통신 | MQTT (엣지 → ESP32-S3), WebSocket (서버 → 대시보드) | 경량 발행/구독으로 제어 지령을 보내고, 대시보드에는 실시간으로 밀어준다. |
| 데이터베이스 | SQLite | 설치가 필요 없고 로컬 로그 저장에 충분하다. |
| 대시보드 | 웹 페이지 (HTML + WebSocket) | 별도 앱 없이 브라우저로 상태를 본다. |
| 알림 시스템 | 이메일 또는 Slack Webhook | 이상 발생 시 관리자에게 즉시 전달한다. |
| 구동기 인터페이스 | 인버터(VFD) 0–10 V 속도 입력 | 산업 현장에서 가장 일반적인 팬 속도 제어 방식이다. |

- 라이선스(가정): 상용화 시 YOLO 모델 라이선스 조건을 확인하고, 필요하면 상업 이용이 자유로운 모델로 교체한다.

## 5. 개발 범위 / 비범위 (Scope)

### 개발 범위 (In Scope)
1. 카메라 영상 기반 실시간 사람 검출 (YOLO nano)
2. 중복 제거·추적·방 영역 카운트 (supervision)
3. 인원 평활화와 팬 단계 결정 로직 (히스테리시스·최소 유지시간 포함)
4. ESP32-S3를 통한 팬 속도 지령 출력 (0–10 V)
5. 인원·팬 단계·전력 절감 추정 로그의 로컬 저장 (SQLite)
6. 관리자 웹 대시보드 (현재 인원, 팬 단계, 일별 추이)
7. 이상 알림 (카메라 끊김, 인원 급변, 통신 오류)
8. 통신 두절·카메라 오류 시 안전 동작 (마지막 안전 단계 유지 또는 100 % 복귀)

### 개발 제외 범위 (Out of Scope)
1. 개인 식별·얼굴 인식 (인원 "수"만 센다)
2. 영상 저장 및 외부(클라우드) 전송
3. 모바일 앱 개발
4. 다국어 지원
5. 클라우드 모델 학습 및 자동 재학습 파이프라인
6. 사용자 권한 관리 (다중 계정)
7. 냉난방 설정온도 등 팬 외 공조 장비 제어
8. 다중 방·건물 통합 관리

## 6. ROI 분석 (Business Value)

### 계산 전제 (가정)
- 도입 규모: 강의실 10실. 각 실의 송풍기는 7.5 kW, 인버터 설치됨.
- 기준 운전: 하루 12시간, 월 22일 상시 100 % 운전 → 실당 월 1,980 kWh.
- 운전 시간 비중: 30 % 25 %, 50 % 30 %, 75 % 25 %, 100 % 20 %.
- 팬 법칙(전력 ∝ 속도³)으로 계산하면 이론상 전력은 상시 100 %의 약 35 %. 인버터·모터 효율 저하와 최소 환기량을 반영해 **실제 절감률은 55 %로 보수적으로 가정**했다.
- 전기요금 150원/kWh. 개발 인건비 시간당 25,000원, 개발 120시간.

### 재무 항목

| 항목 | 산출 근거 | 금액 |
|---|---|---|
| 초기 투자비 (CAPEX) | H/W 35만 원 × 10실 = 350만, AI 모델 초기 개발비 120시간 × 25,000원 = 300만, 모델 라이선스 150만, 설치 공사 30만 × 10실 = 300만 | **11,000,000원** |
| 월 절감액 (Gross Benefit) | 송풍기 전력 절감 1,089 kWh × 150원 × 10실 = 1,633,500원, 외기 냉난방 부하 절감 9만 원 × 10실 = 900,000원 | **2,533,500원** |
| 월 운영비 (OPEX) | 엣지 기기 전력 약 8,640원, 유지보수 200,000원, 모델 재학습 공수 150,000원 (클라우드·API 비용 없음) | **358,640원** |
| 월 순 절감액 (Net Benefit) | 2,533,500 − 358,640 | **2,174,860원** |
| 연간 ROI | (2,174,860 × 12) / 11,000,000 × 100 | **약 237 %** |
| 투자 회수기간 (Payback) | 11,000,000 / 2,174,860 | **약 5.1개월** |

### 최종 판정
**투자 타당.** 가정한 조건에서 약 5개월 만에 투자비를 회수한다. 다만 결과는 송풍기 용량, 운전 시간, 실제 절감률에 크게 좌우된다. PoC 단계에서 실측 전력으로 절감률(가정 55 %)을 검증한 뒤 수치를 확정한다.
