# 과제 보고서: OccuFan의 YOLO 모델 선택·학습·검증

## 1. 선택한 사례
카메라로 방 안 인원 수를 세어 송풍기 풍량 단계(30 / 50 / 75 / 100 %)를 조절하는 인원 연동 팬 제어 시스템(OccuFan)이다.
영상은 엣지 기기(Raspberry Pi 5, CPU)에서만 처리하고 밖으로 보내지 않는다. (PRD 참고)

이 보고서는 오늘 배운 YOLO 학습 HTML(1~6장, 종합 콘솔)과 검증 HTML(0~7), 교재 B2-2·B2-3·B2-4·B2-8·B3·B5의 **모든 단계를 하나씩 따라가며**, 각 단계에서 OccuFan이 무엇을 선택했고 왜 그렇게 했는지 적는다.

## 2. 판단 결과
**YOLO26 · detect · nano(yolo26n.pt)를 COCO 사전학습 가중치에서 시작해 person 1개 클래스로 파인튜닝하고, mAP50·재현율과 제품 지표(인원 수 오차, 풍량 단계 일치율)로 검증한다.**

| 항목 | 선택 | 해당 단계 |
|---|---|---|
| 버전 | YOLO26 | M2, M6 |
| 작업 | detect | M1 |
| 크기 | n (nano) | M4, S7 |
| 클래스 | person 1개 (nc=1, COCO 0번 이름 유지) | M7, S3, S6 |
| 실행 위치 | 온디바이스 (Pi 5 CPU + ONNX Runtime) | M8, V13 |
| 학습 방식 | 사전학습 → 단일 단계 파인튜닝, freeze=10 | S5, S18, S19 |
| 주 지표 | mAP50, 재현율(R) | V5, V7, V9 |
| 제품 지표 | 인원 수 오차, 풍량 단계 일치율, 추론 속도 | V13, V14 |

## 3. 가정
| 항목 | 내용 |
|---|---|
| 카메라 | PRD대로 실내 천장 또는 벽면에 설치한 RGB 카메라 1대 (Pi Camera Module 3 또는 USB), 해상도 고정 |
| 대상 공간 | 대학 강의실·회의실 (인원 0명 ~ 30명 이상) |
| 학습 데이터 | 직접 찍은 방 사진 약 1,500장 계획 (train 1,200 · val 300), 빈 방 포함 (가정) |
| 학습 장비 | Google Colab GPU (T4 16GB) (가정) |
| 배포 장치 | Raspberry Pi 5 CPU + ONNX Runtime (PRD) |
| 판단 주기 | 최근 2초 인원값의 중앙값으로 풍량 단계 결정 (PRD) |

- 아래 단계 중 "실측"이라고 쓴 것은 M9 사전 확인 하나뿐이다.
- 수업 HTML 위젯의 숫자(에폭, 시간, VRAM 등)는 교재의 **개념 모형** 값이다. 실제 학습 결과가 아니다.

## 4. 모델 선택 (M1 ~ M9)

### M1. 작업(task) 고르기
- 근거: 화이트보드 · B2-4 p.74
- 교재: YOLO는 같은 버전 안에서도 작업별 head가 다르다. detect(접미사 없음), seg, pose, cls, obb 다섯 가지다. 파일 이름은 `버전 + 크기 + 작업 + 확장자`(예: `yolo26n-seg.pt`)다.
- **OccuFan 선택: detect → `yolo26n.pt`**
- 이유
  - 제품이 알아야 하는 건 "방에 몇 명 있나" 하나다. 사람마다 박스가 하나씩 나오니 박스 개수가 곧 인원 수다.
  - 방 영역 안 카운트(PolygonZone)도 박스 위치만 있으면 된다.
  - seg는 사람 윤곽 마스크까지 그려서 계산과 라벨링만 늘어난다. pose는 관절 위치라 팬 제어에 쓸 데가 없다.
  - cls는 사진 한 장에 라벨 하나라서 수를 셀 수 없다. obb는 항공·위성 사진처럼 회전된 물체용이다.

### M2. 버전 고르기
- 근거: B2-8 p.166
- 교재: 구버전(v8, v11)을 쓰지 않고 2026 정본 후보(YOLO26, RF-DETR, YOLOE, DINO-X)를 같은 기준으로 잰다.
- **OccuFan 선택: YOLO26**
- 이유
  - YOLO26은 NMS-free다. 한 사람에게 겹쳐 잡힌 박스 중 가장 정확한 하나만 남긴다. 인원 수를 셀 때 중복 박스가 곧 오차라서 직접 이득이다.
  - 후처리가 모델 안에 있어 CPU 배포 코드가 짧아진다. 그래서 PRD 후처리 중 "중복 박스 제거(NMS)"는 생략하고, supervision은 추적(ByteTrack)과 영역 카운트(PolygonZone)에만 쓴다.

### M3. 선택 기준 네 축
- 근거: B2-8 p.165
- 교재: 모델 선택은 취향이 아니라 속도, 정확도(mAP), 라이선스, 엣지 적합성 네 축의 숫자로 정한다.
- **OccuFan 선택: 속도 · 정확도 · 라이선스 · 엣지 네 칸을 모두 채워서 고른다**
- 이유
  - 아래 M4~M8이 이 네 칸을 하나씩 채우는 과정이다.

### M4. 크기 고르기 (속도 ↔ 정확도)
- 근거: B2-8 p.174~175 · 학습 HTML 1장
- 교재: CPU 지연은 n 44.8 ms, s 79.7 ms, m 170.8 ms이고 COCO mAP는 40.9, 48.6, 53.1이다. 이미지 1,500장 규모면 n이 가장 유리하다.
- **OccuFan 선택: n (nano)**
- 이유
  - PRD 목표는 Pi 5 CPU에서 5 FPS 이상이다. GPU 없는 장치라 가장 빠른 n이 맞다.
  - 사람 수는 천천히 바뀐다. 2초 동안의 값을 중앙값으로 묶어 판단하므로 한 장 한 장의 정확도를 극한까지 올릴 필요가 없다.
  - 데이터가 약 1,500장이면 큰 모델은 남는 용량으로 데이터를 외워서 오히려 손해다.
  - 사람은 COCO에서 가장 많이 학습된 클래스라 n으로도 기본 성능이 나온다. 교재 정석대로 n으로 시작하고, 재현율 목표를 못 넘으면 s로 올린다.

### M5. 라이선스
- 근거: B2-8 p.181
- 교재: YOLO26은 AGPL-3.0이다. 제품에 넣어 팔면서 소스를 공개하지 못하면 Enterprise 라이선스가 필요하다.
- **OccuFan 선택: 개발·포트폴리오 단계는 AGPL-3.0, 상용화 시 Enterprise 라이선스**
- 이유
  - 이번 프로젝트는 GitHub에 코드를 공개하는 개인 포트폴리오라 AGPL 조건을 지킬 수 있다.
  - 상용화할 때는 Enterprise 라이선스가 필요하다. PRD의 ROI에 모델 라이선스 150만 원을 넣어 두었다. 비용이 부담되면 Apache 계열(RF-DETR)을 검토한다.

### M6. RF-DETR와 비교
- 근거: B2-8 p.183
- 교재: 엣지·CPU 추론이면 YOLO26, 서버 GPU에서 돌리고 라이선스 자유가 중요하면 RF-DETR이다.
- **OccuFan 선택: YOLO26**
- 이유
  - 팬 제어기는 GPU가 없는 작은 장치(Pi 5)에서 하루 종일 돌아야 한다. CPU에 최적화된 쪽이 맞다.

### M7. 고정 클래스로 충분한가
- 근거: B2-8 p.184
- 교재: 찾을 대상이 COCO 80 클래스 밖이면 YOLOE(제로샷)나 DINO-X를 쓴다. 안에 있으면 YOLO26으로 충분하다.
- **OccuFan 선택: 고정 클래스 1개, person (COCO 0번)**
- 이유
  - 사람은 COCO 0번 클래스다. 말로 대상을 바꿔가며 찾을 일이 없으니 제로샷 모델은 필요 없다.

### M8. 어디서 돌릴까 (엣지 vs 클라우드)
- 근거: B2-8 p.185~186
- 교재: 실시간, 오프라인, 개인정보가 걸리면 온디바이스다. 상시 대량 추론은 클라우드 API가 비싸진다.
- **OccuFan 선택: 온디바이스 (Raspberry Pi 5 CPU + ONNX Runtime)**
- 이유
  - 방 안을 찍는 카메라라서 영상이 밖으로 나가지 않는 것이 중요하다. 사람 수만 내부에서 계산하고 영상은 저장·전송하지 않는다(PRD 지표: 외부 전송 영상 0건).
  - 팬은 하루 종일 돌아서 추론도 상시다. 클라우드 종량 과금은 맞지 않는다.
  - 인터넷이 끊겨도 팬 제어는 계속돼야 한다.

### M9. 사전 확인: yolo26n으로 실제로 세어보기 (실측)
- 근거: 실측 · B2-2 p.39 · B2-8 p.172
- 교재: supervision으로 person만 걸러 세고, 워밍업 3회를 버린 뒤 10회 반복해 CPU 지연을 잰다.
- **OccuFan 결과: yolo26n.pt(학습 전) · conf 0.50 → 4명 · CPU 평균 73.1 ms (±3.2) · 약 13.7 FPS**
- 이유
  - 학습 전 사전학습 모델만으로도 교재 예시 사진(버스)의 4명을 모두 셌다. 화면 가장자리에 반쯤 잘린 사람(0.66)도 잡았다. 같은 conf 0.50에서 yolov8n은 이 사람을 놓쳤다.
  - 이 측정은 2코어 클라우드 CPU 기준이고 방 사진도 아니다. Pi 5 속도와 방 사진 성능은 실제 장치와 데이터로 다시 잰다(V13).
  - 그래도 2초 단위로 판단하는 팬 제어에는 지연이 충분히 짧다는 감은 잡았다.

## 5. 학습 (S1 ~ S27)

### S1. 학습 → 검증 루프 전체 그림
- 근거: B2-4 p.73
- 교재: yolo26n.pt에서 시작해 내 data.yaml로 미세조정하고, val()로 mAP를 잰 뒤, 오탐·미탐 사례를 데이터로 되먹인다.
- **OccuFan 선택: yolo26n.pt → .train(occufan.yaml) → .val() → 되먹임**
- 이유
  - S2~S27이 이 루프의 앞부분(데이터와 학습), V1~V14가 뒷부분(검증과 되먹임)이다.

### S2. 데이터 수집 · 라벨링 · 분할
- 근거: B2-3 p.66
- 교재: 수집 → 라벨링 → 분할 → 증강 → 학습 순서다. 증강은 학습셋에만 하고, train/val은 겹치지 않게 나눈다.
- **OccuFan 선택: 방 사진 약 1,500장 계획 (train 1,200 · val 300)**
- 이유
  - 카메라 설치 방식(천장 또는 벽면)을 하나로 정하고, 실제 설치할 시점 그대로 찍는다. 시점이 바뀌면 다시 학습한다.
  - 0명부터 30명 이상까지 인원을 고루 넣는다. 특히 풍량 단계가 바뀌는 경계(4~5명, 14~15명, 24~25명) 근처 사진을 충분히 넣는다.
  - 낮/밤/조명 꺼짐, 앉음/서 있음/책상에 가려짐, 문 앞을 지나가는 사람을 고루 넣는다.
  - 사람이 한 명도 없는 빈 방 사진을 꼭 넣는다. 빈 방에서 0명이 나와야 팬이 최소 풍량(30 %)으로 내려간다.
  - 같은 날 연속으로 찍은 비슷한 프레임은 train과 val 중 한쪽에만 넣는다. 섞이면 검증 점수가 부풀려진다.
  - 라벨 기준을 하나로 통일한다. 천장 시점이면 보이는 머리·어깨에, 벽면 시점이면 사람 전체에 박스를 친다.
  - 학습 사진은 PoC 때 동의를 받고 찍은 사진이나 공개 데이터셋만 쓴다. 운영 중 영상은 저장하지 않는다는 PRD 원칙과 구분한다.

### S3. YOLO 포맷과 data.yaml
- 근거: B2-4 p.78~79
- 교재: 내 데이터는 이미지와 정규화된 라벨(.txt) 쌍, 그리고 경로·클래스 수·이름을 적은 data.yaml이다.
- **OccuFan 선택: `occufan.yaml` → `nc: 1`, `names: [person]`**
- 이유
  - 클래스는 사람 하나라 nc는 1이고, 라벨 파일 첫 열은 전부 0이어야 한다.

### S4. 가중치 전이 지도
- 근거: 학습 HTML 1장
- 교재: 클래스 수를 바꿔도 새로 초기화되는 건 마지막 분류 컨볼루션뿐이고 나머지는 그대로 넘어온다.
- **OccuFan 선택: 클래스 수 1 → 재초기화 451개, 전이 비율 99.98 %**
- 이유
  - 클래스가 1개라 새로 배워야 하는 부분이 아주 작다. 사전학습 지식(백본·넥)을 거의 전부 이어받고 시작한다.

### S5. 전이 학습 vs 처음부터
- 근거: 학습 HTML 1장
- 교재: 같은 목표 mAP 0.55에 사전학습은 22에폭, 처음부터 학습은 146에폭에 도달한다(개념 모형). 아끼는 건 정확도가 아니라 시간이다.
- **OccuFan 선택: 사전학습 yolo26n.pt에서 출발 (from scratch 안 함)**
- 이유
  - 교재가 예외로 든 열화상·위성처럼 픽셀 특성이 다른 영상이 아니라 일반 RGB 실내 사진이다. 처음부터 학습할 이유가 없다.
  - 약 120시간짜리 프로젝트라 학습 시간을 아끼는 것이 실험 횟수를 늘리는 길이다.

### S6. 클래스 이름 맞추기
- 근거: 학습 HTML 1장
- 교재: 내 데이터의 클래스가 COCO와 같은 개념이면 이름과 번호를 맞춰 그 지식을 이어받을 수 있다.
- **OccuFan 선택: 클래스 이름을 COCO와 같은 `person`(0번)으로 둔다**
- 이유
  - "사람"이나 "occupant"로 바꿀 이유가 없다. COCO의 person과 정확히 같은 개념이다.
  - 클래스 수가 80개에서 1개로 바뀌므로 분류 출력층은 어차피 새로 만들어진다(S4의 451개). 이름을 맞추는 이유는 V1 기준선(COCO 모델)과 학습 후 모델을 같은 이름·같은 번호로 비교하기 위해서다.
  - 대시보드에 한글로 보여주고 싶으면 출력할 때만 바꾼다. .pt 파일 안의 이름은 건드리지 않는다.

### S7. 모델 크기는 작은 것부터
- 근거: 학습 HTML 1장
- 교재: 이미지 1,500장에서는 n이 가장 유리하고, 큰 모델은 남는 용량으로 데이터를 외운다.
- **OccuFan 선택: yolo26n**
- 이유
  - M4와 같은 결론이다. 학습 쪽 근거(데이터 양)와 배포 쪽 근거(Pi 5 CPU 속도)가 둘 다 n을 가리킨다.

### S8. 배치 크기
- 근거: 학습 HTML 2장
- 교재: 배치는 VRAM이 허락하는 최대치까지 올린다. 처음 만지는 GPU면 batch=-1로 자동 산정한다. GPU는 작은 계산을 동시에(병렬) 처리해서 배치가 클수록 빨라진다.
- **OccuFan 선택: `batch=-1` (Colab T4 16GB)**
- 이유
  - 위젯 기준 16GB에서 배치 32일 때 점유율 92 %, VRAM 4.8GB다(개념 모형). 여유가 있으니 자동 산정에 맡긴다.
  - 배치는 속도를 위한 설정이다. 빨라진 만큼 S12 리허설과 재학습을 더 자주 할 수 있다.

### S9. 캐싱
- 근거: 학습 HTML 2장
- 교재: 이미지를 RAM에 올려두면 2에폭째부터 디스크 대기가 사라진다. 첫 에폭은 캐시를 만드느라 더 느리다.
- **OccuFan 선택: `cache=True`**
- 이유
  - 1,500장이면 코랩 RAM에 충분히 올라간다. 최대 150에폭을 돌리니 첫 에폭 손해는 금방 회수된다.

### S10. AMP (혼합 정밀도)
- 근거: 학습 HTML 2장
- 교재: AMP는 기본값 True다. 끄면 느려지고 VRAM을 더 쓰는데 정확도 이득은 없다.
- **OccuFan 선택: `amp=True` (기본값 유지)**
- 이유
  - 바꿀 이유가 없는 항목이다. T4에서 속도와 메모리 모두 이득이다.

### S11. 분산 학습
- 근거: 학습 HTML 2장
- 교재: 기업 규모 데이터셋에서 여러 GPU로 배치를 쪼개는 방법이다.
- **OccuFan 선택: 해당 없음 (GPU 1장)**
- 이유
  - 1,500장, GPU 1장 규모라 필요 없다.

### S12. fraction 리허설
- 근거: 학습 HTML 3장
- 교재: 전체의 일부만으로 먼저 돌려 설정이 끝까지 도는지 확인한다. 이때 나온 성능 숫자는 믿지 않는다.
- **OccuFan 선택: 본 학습 전에 `fraction=0.1`, `epochs=5`로 1회**
- 이유
  - data.yaml 경로, nc=1, 라벨 첫 열이 0인지, 결과 파일이 저장되는지만 본다.
  - 본 학습을 코랩에 걸어두고 자리를 비웠다가 경로 오타로 시간을 날리는 사고를 막는다.

### S13. 증강: scale · mosaic · multi_scale
- 근거: 학습 HTML 3장
- 교재: scale은 피사체를 앞뒤로 움직이는 효과, multi_scale은 입력 해상도 자체를 바꾸는 효과다. 데이터가 적으면(3,000장 미만) mosaic를 낮춘다.
- **OccuFan 선택: `scale=0.5`(기본) · `mosaic=0.5` · `multi_scale=0.0`(끔)**
- 이유
  - 강의실에서는 카메라에 가까운 사람과 먼 사람의 크기 차이가 크다. scale은 기본값으로 유지한다.
  - 1,500장은 교재 기준으로 소형 데이터셋이라 mosaic를 0.5로 낮춘다. 실제 방 화면은 모자이크처럼 생기지 않았다.
  - 카메라가 하나이고 해상도가 고정이라 multi_scale은 필요 없다.

### S14. 에폭과 조기 종료
- 근거: 학습 HTML 4장
- 교재: patience 기본값 100은 파인튜닝에 너무 크다. 파인튜닝이면 10~20으로 낮춘다.
- **OccuFan 선택: `epochs=150` · `patience=15`**
- 이유
  - 위젯(개념 모형)에서 81에폭에 최고점, 96에폭에 자동 종료되고 54에폭을 아낀다.
  - epochs는 상한일 뿐이고, 실제 종료는 val mAP가 15에폭 동안 안 오르면 일어난다.

### S15. optimizer=auto가 고르는 것
- 근거: 학습 HTML 4장
- 교재: 총 반복 횟수(에폭 × 이미지 수 ÷ 배치)가 10,000 미만이면 AdamW, 넘으면 MuSGD를 고른다.
- **OccuFan 선택: 150 × (1,500 ÷ 32) ≈ 7,031회 → AdamW**
- 이유
  - 소규모 학습이라 AdamW 구간이다. 실제 train은 1,200장이라 반복 횟수가 더 적고, 역시 AdamW다.
  - 이 결과를 다음 단계(S16)에서 명시적으로 고정한다.

### S16. lr0가 무시되는 함정
- 근거: 학습 HTML 4장
- 교재: optimizer=auto는 학습률까지 스스로 정해서 내가 준 lr0를 덮어쓴다. 직접 제어하려면 옵티마이저를 명시한다.
- **OccuFan 선택: `optimizer="AdamW"` 명시**
- 이유
  - auto로 두면 배치가 바뀔 때 옵티마이저도 바뀔 수 있다. 재학습(V12)마다 결과를 비교하려면 고정하는 편이 안전하다.

### S17. 학습률 스케줄
- 근거: 학습 HTML 4장
- 교재: warmup_epochs는 시작을 보호하고 lrf는 끝을 안착시킨다. 파인튜닝에서도 웜업 기본값 3을 유지한다.
- **OccuFan 선택: `lr0=0.002` · `lrf=0.01` · `warmup_epochs=3`**
- 이유
  - 0.002는 auto가 AdamW를 고를 때 클래스 1개 기준으로 계산하는 값(0.002 × 5 ÷ (4+1))과 같다. Ultralytics 코드에서 확인했다.
  - 3에폭 웜업 후 직선으로 내려가 최종 학습률은 0.00002가 된다.
  - 사전학습 가중치를 첫 배치부터 크게 흔들지 않도록 웜업을 그대로 둔다.

### S18. 프리징
- 근거: 학습 HTML 5장
- 교재: 소규모 + 유사 도메인이면 freeze=10이다. 백본 대부분을 얼리고 마지막 C2PSA 블록(10번)부터 학습한다. 기본 train은 모든 층을 업데이트한다.
- **OccuFan 선택: `freeze=10`**
- 이유
  - 실내 RGB 사진 속 사람은 COCO와 비슷한 도메인이고, 데이터는 1,500장으로 소규모다. 교재 표의 "소규모 + 유사" 칸에 해당한다.
  - 위젯 기준으로 학습 파라미터 47.9 %, 속도 ×1.29, VRAM ×0.78, 과적합 저항이 올라간다(근사치).
  - 백본을 얼려 두면 적은 데이터로도 COCO에서 배운 "사람 특징"이 무너지지 않는다.

### S19. 2단계 파인튜닝
- 근거: 학습 HTML 5장
- 교재: 1단계에서 헤드를 먼저 맞추고(freeze=10), 2단계에서 백본을 열어(freeze=None, lr0 ≤ 0.001) 전체를 조금 더 맞춘다. 도메인이 COCO와 비슷하면 단일 단계가 이긴다.
- **OccuFan 선택: 단일 단계로 시작 → 천장 시점에서 재현율 목표 미달이면 2단계 추가**
- 이유
  - 벽면 카메라로 찍은 방 사진은 COCO와 격차가 작다. 단일 단계면 충분하다.
  - 천장에서 내려다보면 머리·어깨만 보여 COCO 사진과 달라진다. 이때 1단계 결과의 재현율이 0.90에 못 미치면 2단계를 쓴다. 헤드를 먼저 맞추고 나중에 백본을 여는 순서여야 기존 지식이 무너지지 않는다.
  - 나중에 어두운 방을 위해 열화상 카메라로 바꾸면 그때도 2단계를 검토한다.

### S20. 학습 실행 코드
- 근거: B2-4 p.85
- 교재: data만 내 yaml로 바꾸면 같은 .train()이 내 데이터를 학습한다. 결과는 `runs/detect/train`에 best.pt와 results.png로 남는다.
- **OccuFan 선택: 6장의 "최종 설정" 코드**
- 이유
  - S4~S19에서 정한 값을 한 줄씩 인자로 옮긴 것이다.

### S21. 안 될 때 진단 순서
- 근거: 학습 HTML 6장
- 교재: conf를 낮춰보기 → data.yaml 경로·라벨 개수 확인 → nc와 라벨 번호 범위 → 데이터 양 순서로, 확인이 쉬운 것부터 본다.
- **OccuFan 선택: 학습 전에 val로 라벨 개수 확인을 습관으로**
- 이유
  - nc가 1이니 라벨 파일 첫 열의 최댓값은 0이어야 한다. 라벨링 툴에서 클래스를 하나라도 더 만들었다면 여기서 걸러진다.

### S22. 박스가 안 나오면 conf부터
- 근거: 학습 HTML 6장
- 교재: conf=0.1로 낮춰 뭐라도 나오면 모델은 살아있고 성능이 부족한 것이다.
- **OccuFan 선택: 진단할 때만 `conf=0.1`, 배포는 V4·V8에서 정한 값**
- 이유
  - 사람이 있는데 0명이 나오면 이 단계부터 확인한다.

### S23. mAP가 일찍 정체될 때
- 근거: 학습 HTML 6장
- 교재: 에폭을 늘리는 건 거의 답이 아니다. 다양성 부족, 클래스 불균형, 과한 증강, 너무 작은 객체 순으로 본다.
- **OccuFan 선택: 다양성 먼저 → 넓은 강의실이면 `imgsz=1280` 검토**
- 이유
  - 데이터는 장수가 아니라 상황 가짓수로 센다. 조명, 시간대, 앉은 자세, 가림을 늘린다.
  - 회의실 크기에서는 사람이 충분히 커서 640이면 된다. 넓은 강의실 뒷줄처럼 사람이 작게 찍히면 1280을 검토하되, VRAM 때문에 배치를 줄이고 Pi 5 속도(V13)도 다시 잰다.

### S24. 클래스 불균형 (cls_pw)
- 근거: 학습 HTML 6장
- 교재: 희귀 클래스가 mAP를 깎을 때 역빈도 가중치를 0.25부터 준다.
- **OccuFan 선택: `cls_pw=0.0` (기본, 해당 없음)**
- 이유
  - 클래스가 person 하나뿐이라 불균형이 생길 수 없다.

### S25. 치명적 망각
- 근거: 학습 HTML 6장
- 교재: 새 데이터에 기존 클래스가 안 나오면 모델이 그 클래스를 잊는다.
- **OccuFan 선택: 망각 허용 (person 외 79개 클래스는 안 씀)**
- 이유
  - 이 제품은 사람만 센다. 자동차나 개를 잊어도 문제가 없어서 COCO 데이터를 섞을 필요가 없다.
  - 다만 의자, 옷걸이에 걸린 옷, 포스터 속 사람처럼 헷갈리는 배경은 빈 방 사진으로 따로 넣어 "사람 아님"을 가르친다.

### S26. 종합 콘솔로 확인
- 근거: 학습 HTML 종합 콘솔
- 교재: 시나리오를 고르고 설정을 바꿔 val mAP, 학습 시간, VRAM, 과적합 위험을 동시에 본다(개념 모형).
- **OccuFan 선택: 조건이 같은 시나리오(1,500장 · 유사 도메인 · 16GB)의 권장 설정 = 내 설정**
- 이유
  - 모델 n, freeze=10, 배치 32, 640, mosaic 0.5, 캐시 RAM, AMP 켬, 150에폭으로 교재 권장값과 같다.
  - 결과(개념 모형): 59에폭에서 최고점, 총 26분, VRAM 3.8GB, 과적합 위험 낮음.
  - 진단이 "VRAM을 24 %만 쓴다, 배치를 올려라"라고 한다. 그래서 S8에서 batch=-1로 둔다.

### S27. 배포용 체크리스트
- 근거: 학습 HTML 종합 콘솔
- 교재: 학습 전, 설정, 데이터가 적을 때, 도메인이 다를 때, 결과가 안 나올 때 다섯 묶음이다.
- **OccuFan 선택: 경로·nc 확인, 라벨 개수, fraction=0.1, n부터, batch=-1, cache=True, amp=True, patience, optimizer 명시, freeze=10, mosaic=0.5, 크기 올리기 전에 데이터 점검, conf=0.1 진단, 다양성 확보에 체크**
- 이유
  - 도메인이 다를 때(freeze=None, 2단계)는 천장 시점에서 재현율이 부족할 때만 쓴다(S19).
  - cls_pw는 S24 이유로 해당 없고, imgsz=1280은 S23 조건에서만 쓴다.

## 6. 최종 학습 설정

```python
from ultralytics import YOLO

model = YOLO("yolo26n.pt")                 # M1~M4: YOLO26 · detect · nano (COCO 사전학습)

model.val(data="occufan.yaml")             # V1: 학습 전 기준선 + 라벨 개수 확인 (S21)

model.train(data="occufan.yaml",           # S12: 리허설 (성능 숫자는 안 믿음)
            fraction=0.1, epochs=5, batch=-1)

model = YOLO("yolo26n.pt")                 # 본 학습은 처음 가중치로 다시 시작
model.train(
    data="occufan.yaml",                   # S3: nc: 1, names: [person]
    epochs=150, patience=15,               # S14
    imgsz=640, batch=-1,                   # S8, S23
    cache=True, amp=True,                  # S9, S10
    optimizer="AdamW", lr0=0.002,          # S15~S17
    lrf=0.01, warmup_epochs=3,             # S17
    freeze=10,                             # S18
    mosaic=0.5, scale=0.5,                 # S13 (multi_scale는 기본 0.0 = 끔)
)

best = YOLO("runs/detect/train/weights/best.pt")
best.val(data="occufan.yaml")              # V3~V9: 기본 conf로 결과표·PR 곡선
best.export(format="onnx")                 # V13: 배포용 변환 후 parity 확인
```

## 7. 검증 (V1 ~ V14)

### V1. 기준선 먼저 재기
- 근거: B2-4 p.82
- 교재: 학습 전에 사전학습 모델의 mAP를 같은 검증셋으로 재 둔다. 학습 후 같은 val을 다시 돌려 올랐는지로 개선을 판단한다.
- **OccuFan 선택: yolo26n.pt(학습 전)로 내 val 300장 → 기준선 기록**
- 이유
  - 사람은 COCO에 이미 있어서 학습 전에도 점수가 꽤 나올 수 있다. 파인튜닝이 정말 이득인지 이 숫자와 비교해야 말할 수 있다.
  - 기준선보다 못하면 학습 설정이나 데이터가 잘못된 것이다.
  - 천장 시점이면 기준선이 낮게 나올 수 있다. 이 값이 S19(2단계 여부)를 판단하는 출발점이다.

### V2. IoU에서 mAP까지 흐름
- 근거: B2-4 p.80
- 교재: IoU로 맞음·오탐·미탐을 가르고, P·R 곡선 아래 넓이(AP)를 클래스끼리 평균해 mAP를 낸다.
- **OccuFan 선택: V3~V9를 이 순서대로 읽는다**
- 이유
  - 클래스가 1개라 마지막 "클래스 평균" 단계는 사실상 person의 AP 그대로다.

### V3. 결과표 읽기
- 근거: 검증 HTML 0
- 교재: 학습이 끝나면 Class, Images, Instances, P, R, mAP50, mAP50-95 표가 나온다. Instances가 적으면 그 점수는 덜 믿을 만하다.
- **OccuFan 선택: 결과표는 `all` 한 줄 (= person)**
- 이유
  - 클래스가 하나면 Ultralytics는 클래스별 줄을 따로 찍지 않는다(nc > 1일 때만 출력). all 줄이 곧 person의 성적이다.
  - 먼저 Instances(정답 사람 박스 수)가 충분한지 본다. 강의실 사진이라 검증 300장에 사람 박스가 수천 개는 나와야 한다.
  - 빈 방 사진은 Instances에는 안 잡히지만 FP를 확인하는 데 꼭 필요하다.

### V4. 신뢰도 임계값 (conf)
- 근거: 검증 HTML 1 · B2-3 p.57
- 교재: 임계값을 올리면 확실한 것만 남아 오검출이 줄고, 내리면 놓치는 건 줄지만 잡음이 는다.
- **OccuFan 선택: 배포 conf=0.50에서 시작 → V8 PR 곡선을 보고 조정**
- 이유
  - 사전 확인(M9)에서 0.50으로 4명을 모두 셌다. 출발점으로 삼는다.
  - conf가 너무 높으면 사람을 놓쳐 풍량이 모자라고(환기 부족), 너무 낮으면 유령 인원 때문에 빈 방에서도 팬이 세게 돈다(전력 낭비).

### V5. IoU 기준
- 근거: 검증 HTML 2 · B2-4 p.81
- 교재: IoU = 겹친 넓이 ÷ 합친 넓이다. 0.50 기준이면 대충 맞아도 인정하고, 0.95는 거의 포개져야 한다.
- **OccuFan 선택: 주 지표 mAP50 · 보조 지표 mAP50-95**
- 이유
  - 위젯에서 예측 박스를 정답 쪽으로 끌어 IoU 0.50으로 맞추면 경계에서 정답으로 인정된다.
  - 인원 세기에는 박스가 픽셀 단위로 정확할 필요가 없다. 사람마다 박스가 하나씩만 나오면 된다. 그래서 관대한 mAP50을 주 지표로 본다.
  - mAP50-95가 유난히 낮으면 박스가 대충이라는 신호라 기록은 해둔다.

### V6. 채점: TP · FP · FN
- 근거: 검증 HTML 3
- 교재: 예측마다 맞힘(TP), 틀림(FP), 놓침(FN)으로 나눈다. FP 이유는 물체 없는 곳, 클래스 틀림, 중복 검출, IoU 부족이다.
- **OccuFan 선택: FP = 유령 인원, FN = 놓친 사람으로 읽는다**
- 이유
  - 위젯에서 고른 '사람 0.52' 박스는 표지판 기둥에 찍힌 FP였다. 이유는 "물체가 없는 곳"이다.
  - 방에서는 옷걸이, 의자에 걸린 외투, 포스터, 거울·창문에 비친 사람이 이런 FP가 된다. 이 사진들을 모아 V12 되먹임에 쓴다.
  - YOLO26은 NMS-free라 "중복 검출" FP는 적을 것으로 본다. 실제로 그런지 검증에서 확인한다.

### V7. 정밀도와 재현율
- 근거: 검증 HTML 4
- 교재: 정밀도 = TP ÷ (TP+FP), 재현율 = TP ÷ (TP+FN)이다. conf를 올리면 정밀도가 오르고 재현율이 내려가는 시소 관계다.
- **OccuFan 선택: 목표 R ≥ 0.90 · P ≥ 0.85 (제안값)**
- 이유
  - 사람을 놓치면(R 낮음) 인원이 적게 세어져 환기가 부족해진다. 실내 공기질에 직접 닿아서 재현율을 조금 더 높게 잡았다.
  - 유령 인원 1명은 경계 근처에서만 풍량 한 단계 차이를 만들고, 2초 중앙값으로 상당 부분 걸러진다. 그래서 정밀도 목표는 조금 낮게 잡았다.
  - 이 숫자는 교재나 PRD가 준 값이 아니라 제품 기준으로 정한 목표다. 실제 val 결과를 보고 다시 조정한다.

### V8. AP: PR 곡선 아래 넓이
- 근거: 검증 HTML 5 · B2-4 p.83
- 교재: conf를 1에서 0까지 내리며 찍은 점들을 이은 곡선의 넓이가 AP다. val 때는 conf를 0.001처럼 거의 0으로 두고 곡선 전체를 그린다.
- **OccuFan 선택: val은 기본 conf(0.001)로 · 배포 conf는 곡선에서 R ≥ 0.90을 지키는 가장 높은 값**
- 이유
  - val과 predict의 conf는 용도가 다르다. val에서 conf를 0.5로 올리면 곡선이 잘려 AP가 틀리게 나온다.
  - BoxPR_curve.png를 보고 V7 목표를 만족하는 지점을 골라 V4의 배포 conf를 정한다.

### V9. mAP: 평균을 한 번 더
- 근거: 검증 HTML 6
- 교재: mAP50은 클래스별 AP의 평균, mAP50-95는 IoU 기준 10단계 AP의 평균이다.
- **OccuFan 선택: 목표 mAP50 ≥ 0.85 · 기준선(V1)보다 높을 것**
- 이유
  - 클래스가 person 하나라 mAP50은 곧 person의 AP50이다. 약한 클래스가 평균을 끌어내릴 일은 없다.
  - 0.85는 교재 B5의 KPI 예시(detect_mAP ≥ 0.85) 형식을 빌려 정한 목표다.

### V10. 결과 패턴별 처방
- 근거: 검증 HTML 7
- 교재: P↑R↓, P↓R↑, mAP50↑50-95↓, 전부 낮음 네 가지 패턴과 처방이다.
- **OccuFan 선택: 패턴별로 할 일을 미리 정해둔다**
- 이유
  - P 높고 R 낮음 → 놓친 상황(어두운 방, 가려진 사람, 뒷줄의 작은 사람) 사진 추가, conf 낮추기.
  - P 낮고 R 높음 → 빈 방·옷걸이·포스터 같은 배경 사진 추가, conf 올리기.
  - mAP50 높고 50-95 낮음 → 인원 세기에는 큰 문제가 아니다. 라벨 박스를 다듬는 건 후순위다.
  - 전부 낮음 → S21 진단 순서로 data.yaml과 라벨부터 확인한다.

### V11. 학습 곡선 확인
- 근거: B2-4 p.85~86
- 교재: results.png에 box·cls·dfl 손실과 mAP가 에폭별로 모인다.
- **OccuFan 선택: results.png에서 val mAP가 평평해진 지점과 patience 종료 지점 확인**
- 이유
  - train 손실은 계속 내려가는데 val mAP가 내려가기 시작하면 외우는 중(과적합)이다. freeze나 데이터 다양성을 다시 본다.

### V12. 되먹임 루프
- 근거: B2-4 p.91
- 교재: 오탐·미탐 이미지를 모아 라벨을 추가·수정한 뒤 재학습한다. 코드가 아니라 데이터가 mAP를 올린다.
- **OccuFan 선택: FP·FN 사진 모으기 → 라벨 보강 → 재학습 → 같은 val로 재측정**
- 이유
  - 검증셋은 고정한다. 매번 바꾸면 이전 결과와 비교할 수 없다.
  - 재학습은 사람이 직접 판단해서 한다. 자동 재학습 파이프라인은 PRD의 개발 제외 범위다.

### V13. 속도 검증과 ONNX 변환
- 근거: B2-8 p.172 · B3 p.29
- 교재: 워밍업 3회를 버리고 10회 재서 평균·표준편차로 말한다. 배포 전에는 ONNX로 변환하고 원본과 결과가 같은지(parity) 확인한다.
- **OccuFan 선택: best.pt → best.onnx 변환 후 parity 확인 · Pi 5에서 10회 벤치 · 목표 5 FPS 이상 (1회 200 ms 이하)**
- 이유
  - PRD 목표가 Pi 5 CPU에서 5 FPS 이상이다. 2초 동안 약 10장을 모아 중앙값을 내려면 이 속도가 필요하다.
  - 같은 사진을 .pt와 .onnx로 돌려 인원 수가 같은지 본다. 변환 과정에서 결과가 달라지면 배포 장치에서만 틀리는 문제가 생긴다.
  - M9의 73 ms는 클라우드 CPU 수치라서 Pi 5에서는 다시 잰다.

### V14. 제품 지표와 KPI 표
- 근거: B5 p.88
- 교재: 지표마다 무엇을(metric), 얼마나(target), 어떻게(how)를 채운다. how 없는 지표는 지표가 아니다.
- **OccuFan 선택: mAP50 · R · P · 인원 수 오차 · 풍량 단계 일치율 · 추론 속도**
- 이유
  - mAP만으로는 "팬이 제대로 도는가"를 말할 수 없다. 그래서 제품 지표를 더한다(교재 밖, 추가한 항목).
  - 인원 수 오차: val 사진마다 |실제 인원 − 센 인원|의 평균. PRD 목표대로 15명 이하 구간 ≤ 1명, 15명 초과 구간은 오차율 ≤ 10 %.
  - 풍량 단계 일치율: 실제 인원으로 정한 단계와 모델 인원으로 정한 단계가 같은 비율. 1명 차이가 단계를 바꾸는 경계(4↔5, 14↔15, 24↔25명) 근처 사진은 따로 본다.
  - 25명 이상은 모두 100 %라서 이 구간은 정확한 인원보다 "25명 이상으로 세는가"가 중요하다.
  - 검증 300장 중 일부는 학습에 쓰지 않은 다른 방·다른 날짜 사진으로 채워, 처음 보는 방에서도 되는지 확인한다.

## 9. 가정과 한계
- 이 보고서는 오늘 수업(학습 HTML, 검증 HTML, 교재 B2·B3·B5)에서 배운 학습·검증 단계를 OccuFan에 적용한 진행 계획이다. 수업에서 단계별 개념과 위젯 실습을 마쳤고, OccuFan 전용 데이터(방 사진)로 하는 실제 학습·검증은 데이터를 모은 뒤 진행한다.
- 실제로 측정한 값은 M9 사전 확인(yolo26n, 사진 1장, 클라우드 CPU) 하나뿐이다.
- 수업 위젯의 에폭·시간·VRAM 숫자는 개념 모형 값이다.
- 사진 1,500장, train 1,200 · val 300, Colab T4 사용은 가정이다.
- mAP50·재현율·정밀도·풍량 단계 일치율·빈 방 오검출 목표는 PRD에 없는 제안값이다. 첫 학습 결과를 보고 조정한다.
- 천장 시점은 COCO 사진과 달라 정확도가 낮을 수 있다. 이 경우 머리·어깨 데이터를 보강하고 2단계 학습(S19)을 한다.
