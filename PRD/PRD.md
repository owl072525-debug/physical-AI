# PRD: 인원 연동 팬 제어 시스템 (가칭 OccuFan)

## 제품 개요

| 항목 | 내용 |
|---|---|
| 제품명 | 인원 연동 팬 제어 시스템 (가칭 OccuFan) |
| 주요 입력 데이터 | 실내 천장·벽면 카메라 영상 (프레임 단위), 방 영역 설정값(좌표) |
| 주요 출력(행동) | 실내 인원 수 → 팬 풍량 단계(30 / 50 / 75 / 100 %) 결정 → 송풍기 인버터에 속도 지령(0–10 V) 전송 |
| 대상 공간 | 인원 변동이 큰 실내 공간 (대학 강의실·회의실 등), 송풍기에 인버터(VFD)가 설치된 곳 (가정) |
| **구현 범위** | **이번 프로젝트는 소형 DC 팬(공조 송풍기의 축소 모델)으로 프로토타입을 만든다. 실제 송풍기 인버터(0–10 V) 연동은 제품 목표이며 이번 범위 밖이다. (프로토타입 범위는 가정이며, 실제 제작 범위는 과정 안내에 따라 확정한다.)** |

## 1. 문제 정의 (Problem Statement)

### 현재 존재하는 문제
- 많은 건물에서 송풍기(AHU·환기팬)는 사람이 있든 없든 **고정 풍량(상시 100 %)** 으로 운전한다.
- 인원이 적을 때는 과잉 환기로 전력과 외기 냉난방 부하가 낭비되고, 인원이 몰릴 때는 환기가 부족해 실내 공기질이 나빠진다.

### 기존 방식의 한계
- **시간표 기반 운전**: 실제 사용 여부와 무관하게 정해진 시각에 운전한다. 휴강·공실을 반영하지 못한다.
- **CO₂ 센서 기반 제어**: 인원이 바뀐 뒤 농도가 변할 때까지 수 분 이상 늦게 반응한다.
- **인체 감지 센서(PIR)**: "있다/없다"만 알 수 있어 인원 규모에 따른 단계 제어가 불가능하다.

### 핵심 가치
- 인원 수를 **즉시** 파악해 필요한 만큼만 환기한다 → 송풍기 전력과 외기 부하 절감.
- 영상 원본을 저장·외부 전송하지 않고 기기 안에서 처리한다 → 개인정보 부담 최소화.

### 왜 AI가 필요한가
- 사람의 수를 세려면 영상 속 사람을 구분하고 같은 사람을 중복 없이 이어서 봐야 한다. 규칙 기반 영상처리(배경 차분 등)는 조명 변화와 사람이 겹치는 상황에서 오차가 크다.
- 사람 검출 AI 모델(YOLO 계열)과 추적·카운트 후처리(supervision)를 조합하면 현장 조건에서 안정적으로 인원을 셀 수 있다.

## 2. 사용자 시나리오 (User Scenario)

| 단계 | 내용 |
|---|---|
| 1. 설치 | 관리자가 카메라와 엣지 기기(Raspberry Pi 5)를 실내에 설치하고, ESP32-S3 제어 모듈을 송풍기 인버터의 0–10 V 입력에 연결한다. **(프로토타입은 팬 드라이버를 거쳐 소형 DC 팬에 연결한다.)** 대시보드에서 방 영역(다각형)과 단계 기준 인원을 설정한다. |
| 2. 데이터 수집 | 카메라가 영상을 연속 촬영하고, 엣지 기기가 프레임을 메모리에서만 처리한 뒤 즉시 폐기한다. |
| 3. 분석 | AI 모델이 사람을 검출하고, **추적(ByteTrack)을 거쳐** 설정한 방 영역 안의 인원 수를 계산한다. |
| 4. 판단 | 최근 2초 인원값을 평활화(중앙값)하고, 인원 기준표와 히스테리시스·최소 유지시간 규칙을 적용해 팬 단계를 결정한다. |
| 5. 제어 | 결정된 단계를 MQTT로 ESP32-S3에 보내고, ESP32-S3가 인버터에 해당 풍량의 속도 지령을 출력한다. **(프로토타입: PWM으로 소형 팬의 속도를 바꾼다.)** |
| 6. 확인·후속 | 관리자는 대시보드에서 현재 인원, 팬 단계, 일별 전력 절감 추정치를 확인한다. 카메라 오류·인원 급변 등 이상 시 알림을 받고 설정을 조정한다. |

### 단계 기준표 (가정)

| 평활 인원 | 팬 단계 | 풍량 지령 | **내릴 때 기준** |
|---|---|---|---|
| **0–5명** | 0단계 | 30 % (최소 환기 유지) | **—** |
| **6–11명** | 1단계 | 50 % | **3명 이하 → 0단계** |
| **12–29명** | 2단계 | 75 % | **9명 이하 → 1단계** |
| **30명 이상** | 3단계 | 100 % | **27명 이하 → 2단계** |

- 내릴 때는 기준보다 2명 더 줄어야 단계를 내린다 (히스테리시스).
- 한 단계는 최소 60초 이상 유지한다 (잦은 전환 방지).
- **근거(가정): 대학 강의실 사용 유형을 기준으로 정했다. 공실(0명)은 최소 환기, 소규모 과제 모임 6명, 팀 두 개 12명, 정규 수업 30명을 각 단계의 기준으로 삼는다. 인원이 늘수록 환기·냉방 필요량이 커지며(환기량은 인원에 비례, 1인당 발열량은 현열 약 75 W·잠열 약 55 W로 가정), 이 방향으로 단계를 정했다.**

## 4. 기술 스택 (Technology Stack)

| 구성 | 사용 기술 | 선정 이유 |
|---|---|---|
| 카메라 | Raspberry Pi Camera Module 3 (CSI) 또는 USB 카메라 | Pi 5와 직접 연결되고 저렴하며 자료가 많다. |
| 센서 | CO₂ 센서 (NDIR, 검증용) **· I2C로 ESP32-S3에 연결** | 제어에는 쓰지 않고 "환기 품질이 유지되는가"를 검증하는 기준값으로만 쓴다. |
| MCU | **ESP32-S3 (1개)** | 저가·저전력이며 Wi-Fi 내장. **센서 읽기와 팬 속도 출력을 한 보드가 맡는다. 0–10 V 지령은 PWM/DAC 변환 모듈로 만든다(제품 목표).** |
| Edge AI | Raspberry Pi 5 (CPU, ONNX Runtime) | 별도 가속기 없이 경량 모델이 현장에서 돈다. 클라우드 왕복 지연이 없다. |
| AI 모델 | **YOLO26 nano (yolo26n, COCO person 클래스)** | 경량이라 CPU에서 실시간 처리가 가능하다. **NMS가 모델 안에서 처리되는 구조다.** 천장 시점 정확도가 낮으면 머리·어깨 데이터로 파인튜닝한다. |
| 후처리 | supervision (**ByteTrack, PolygonZone**) | **같은 사람 추적과 방 영역 내 카운트를 처리한다.** |
| 서버 | FastAPI (Pi 5 내 동작) | 가볍고 API 설계가 쉬워 대시보드·제어 로직과 연결하기 좋다. |
| **센서 연결 (센서 ↔ 컴퓨터)** | **카메라 → Pi 5: CSI 케이블(또는 USB), CO₂ 센서 → ESP32-S3: I2C** | **가까운 거리에서 영상처럼 큰 데이터를 안정적으로 받아야 해서 유선으로 연결한다.** |
| **통신 (컴퓨터 ↔ 컴퓨터)** | MQTT over Wi-Fi (Pi 5 → ESP32-S3), WebSocket (서버 → 대시보드) | 경량 발행/구독으로 제어 지령을 보내고, 대시보드에는 실시간으로 밀어준다. **두 기기가 고정이고 상시 전원과 공유기가 있어 Wi-Fi의 전력·인프라 부담이 없다.** |
| 데이터베이스 | SQLite | 설치가 필요 없고 로컬 로그 저장에 충분하다. |
| 대시보드 | 웹 페이지 (HTML + WebSocket) | 별도 앱 없이 브라우저로 상태를 본다. |
| 알림 시스템 | 이메일 또는 Slack Webhook | 이상 발생 시 관리자에게 즉시 전달한다. |
| 구동기 인터페이스 | **제품 목표: 인버터(VFD) 0–10 V 속도 입력 / 프로토타입: PWM → 팬 드라이버(MOSFET 또는 TB6612FNG) → 소형 DC 팬(12 V, 가정)** | 인버터 0–10 V는 산업 현장에서 가장 일반적인 팬 속도 제어 방식이다. **프로토타입은 같은 제어 구조를 소형 팬으로 축소해 검증한다.** |
| **전원 (가정)** | **12 V 어댑터 → Buck 5 V(Pi 5용 5 A급, ESP32-S3용 별도), 팬 전원은 12 V 직접 공급, 모든 GND 공통 연결** | **상시 전원이 있어 배터리가 필요 없다. Pi와 ESP32 전원을 나눠 한쪽 노이즈가 다른 쪽으로 번지는 것을 줄인다.** |

- 라이선스(가정): 상용화 시 YOLO 모델 라이선스 조건을 확인하고, 필요하면 상업 이용이 자유로운 모델로 교체한다.

### **4-1. 하드웨어 구성과 연결**

**MCU 배치**
- **MCU는 ESP32-S3 1개로 한다. 맡는 일이 센서(CO₂) 읽기와 팬 속도 출력뿐이라 핀과 처리량이 충분하고, 부품이 늘수록 연결·전원 문제가 늘어나므로 단순하게 유지한다.**
- **생각은 SBC(Pi 5), 제어는 MCU(ESP32-S3)가 맡는다. 팬 제어 타이밍이 안정적이고, Pi가 멈춰도 안전 동작을 유지할 수 있으며, 모터 노이즈가 Pi와 센서에 번지는 것을 줄인다.**
- **배치: Pi 5는 카메라와 CSI 케이블 길이 안에 두고, ESP32-S3는 팬 드라이버 가까이에 두어 PWM 선을 짧게 한다.**
- **확장(이번 범위 밖): 팬이 여러 대면 팬마다 MCU를 두고 ESP-NOW 1:N 브로드캐스트로 같은 단계를 한 번에 전달한다.**

**연결 구간**

| 구간 | 방식 | 보내는 것 |
|---|---|---|
| **카메라 → Pi 5** | **CSI 케이블(또는 USB)** | **영상** |
| **Pi 5 ↔ ESP32-S3** | **Wi-Fi (MQTT)** | **단계 명령 / 상태** |
| **CO₂ 센서 → ESP32-S3** | **I2C** | **농도 값** |
| **ESP32-S3 → 팬 드라이버** | **PWM(GPIO)** | **팬 속도** |
| **팬 드라이버 → 소형 DC 팬** | **12 V 전원선** | **회전** |

**통신 방식 선택 근거 (Pi 5 ↔ ESP32-S3)**
- **BLE: 1:1이고 느리며 거리가 짧아 장점이 없다.**
- **ESP-NOW: ESP 보드끼리만 통신해 Pi 5와 직접 연결할 수 없다. 중계 보드가 필요해 복잡해진다.**
- **이더넷: 가장 안정적이지만 ESP32-S3에 별도 모듈이 필요하다.**
- **Wi-Fi(MQTT): 두 기기가 고정이고 상시 전원과 공유기가 있어 약점이 문제되지 않고, 대시보드 연동에도 맞아 선택한다.**

**안전 동작**
- **ESP32-S3는 지령이 일정 시간 오지 않으면 마지막 안전 단계를 유지하거나 100 %로 복귀한다. (시간 기준은 추후 정한다.)**

## 5. 개발 범위 / 비범위 (Scope)

### 개발 범위 (In Scope)
1. 카메라 영상 기반 실시간 사람 검출 (**YOLO26 nano**)
2. **추적·방 영역 카운트 (supervision: ByteTrack, PolygonZone)**
3. 인원 평활화와 팬 단계 결정 로직 (히스테리시스·최소 유지시간 포함)
4. ESP32-S3를 통한 팬 속도 지령 출력 (**프로토타입: PWM으로 소형 DC 팬 제어 / 제품 목표: 0–10 V 인버터 지령**)
5. 인원·팬 단계·전력 절감 추정 로그의 로컬 저장 (SQLite)
6. 관리자 웹 대시보드 (현재 인원, 팬 단계, 일별 추이)
7. 이상 알림 (카메라 끊김, 인원 급변, 통신 오류)
8. 통신 두절·카메라 오류 시 안전 동작 (마지막 안전 단계 유지 또는 100 % 복귀)

### 개발 제외 범위 (Out of Scope)
1. 개인 식별·얼굴 인식 (인원 "수"만 센다)
2. 영상 저장 및 외부(클라우드) 전송
3. 모바일 앱 개발
4. 다국어 지원
5. 클라우드 모델 학습 및 자동 재학습 파이프라인
6. 사용자 권한 관리 (다중 계정)
7. 냉난방 설정온도 등 팬 외 공조 장비 제어
8. 다중 방·건물 통합 관리
9. **실제 공조기·송풍기 인버터 연동 (제품 목표, 이번 범위 밖)**
10. **팬 여러 대 확장 (팬마다 MCU, ESP-NOW 브로드캐스트)**

## 6. ROI 분석 (Business Value)

### 계산 전제 (가정)
- 도입 규모: 강의실 10실. 각 실의 송풍기는 7.5 kW, 인버터 설치됨.
- 기준 운전: 하루 12시간, 월 22일 상시 100 % 운전 → 실당 월 1,980 kWh.
- 운전 시간 비중: 30 % 25 %, 50 % 30 %, 75 % 25 %, 100 % 20 %.
- 팬 법칙(전력 ∝ 속도³)으로 계산하면 이론상 전력은 상시 100 %의 약 35 %. 인버터·모터 효율 저하와 최소 환기량을 반영해 **실제 절감률은 55 %로 보수적으로 가정**했다.
- 전기요금 150원/kWh. 개발 인건비 시간당 25,000원, 개발 120시간.
